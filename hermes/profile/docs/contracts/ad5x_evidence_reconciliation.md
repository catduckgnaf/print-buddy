# AD5X evidence reconciliation

## Conflict handling
1. Identify field meaning, actual installed firmware/source version, native versus screenless mode and adapter provenance before deciding authority. A fresh read can still be inappropriate or unreliable for that mode.
2. Compare near-concurrent readings and timestamp each, preserving exact reported values and operator observations separately. Do not silently choose the account that makes launch easiest.
3. Do not translate nativeAPIprinting into proven physical execution. Distinguish pending, preparing, actually executing and canceled using receipts, status/message/progress/time/targets and mode-correct observations; missing evidence remains unresolved.
4. Native occupancy trueall4 and operator-reported all-loaded conflict with ZMod falseall4 in this installednative mode. Do not use those ZMod flags alone as emptyfeeder proof. Conversely retain materially verified contradictory evidence for investigation, not blanket operator-overrides-all.
5. Critical mapping/readiness unknown blocks launch BEFORE upload and approval consumption, but blockage is not proof filament absent or user error. Gather specific decisive evidence, not repeat loading questions.
6. LogicalT0 physicalslot4 must be verified through actual remote start/map implementation. Generic wiki examples and green RGB metadata do not establish current physical routing. SET_EXTRUDER_SLOT bookkeeping is not a filament switch. Do not assume slot4=T3.
7. Never automatically clear a potentially active job without explicit user direction. Cancellation uncertain acceptance is not retried. Preserve receipts and native/Moonraker readback. See ad5x_repeatable_job_clear.md.
